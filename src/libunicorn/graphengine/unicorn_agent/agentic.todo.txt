Unicorn Graph Engine Agentic TODO
=================================

Current state
-------------

The agentic flow is no longer just an idea. We already have:

- an Agent panel in the graph engine UI
- provider configuration controls in the UI
- a client-side transcript and tool/evidence trace
- a Unicorn-native tool registry exposed in the browser
- a provider-facing turn payload builder
- a client-side provider turn loop with explicit tool-call handling
- a mock provider adapter that exercises the contract today

New invariant:

- graphengine is now intended to run only with a backend connection
- if the user is on one machine, the backend should run locally and the UI
  should connect to `localhost`
- the agent layer should converge on one backend-grounded tool/data path, not
  separate local and remote semantics

Reference docs already in place:

- `provider_turn_contract.txt`
- `graphengine_agent_registry.txt`

Those two files now define the current V1 contract better than this TODO should.
This TODO should focus on what is still missing.


Implemented V1 foundations
--------------------------

Already present in the UI/runtime:

- `buildAgentContext()` as a canonical graph context snapshot
- a constrained tool registry for current graph actions and backend-backed views
- iterative provider turn execution with:
  - provider request payload assembly
  - validated tool calls
  - tool-result reinjection
  - final-answer rendering
- mock-mode end-to-end behavior for local experimentation

Currently available Unicorn-native tools:

- `get_graph_context`
- `list_selected_datasets`
- `get_selected_nodes`
- `get_node_details`
- `get_table_view`
- `select_taxon`
- `focus_taxon`
- `center_root`


What is not done yet
--------------------

1. Remove local-vs-remote semantic drift from the agent layer.
The architecture decision is now backend-required mode. That means:

- no separate local dataset/tree/report tool behavior
- no provider-facing ambiguity about which data path is authoritative
- localhost remains the simple single-machine workflow

2. Real provider adapters.
The UI already exposes provider/model controls for OpenAI and Google, but the
runtime is still mock-mode only. We need real adapters that map the Unicorn
turn contract onto provider SDK/API calls.

3. Provider auth/runtime policy.
We need to decide:

- whether API keys remain frontend-only during prototype mode
- whether real provider calls happen directly from the client or through the
  backend
- what error, retry, and rate-limit behavior should look like

4. Expand the Unicorn-native tool registry carefully.
Likely next additions:

- `get_subtree_report`
- `expand_taxon`
- `highlight_taxa`
- `clear_agent_highlights`

These should be added only if they correspond cleanly to current Unicorn UI or
backend behavior.

5. Tighten the evidence trail UX.
The current transcript/tool trace is functional, but we should make it easier
for a user to answer:

- what tool the agent called
- what scope/filter context it used
- what node/report the answer is grounded in
- what UI action the agent triggered

6. Decide memory/persistence policy for conversation state.
We need a deliberate policy for:

- transcript persistence across reloads or not
- whether agent turns are tied to one graph session
- what gets invalidated when dataset selection or taxonomy changes


Near-term agentic priorities
----------------------------

1. Ship one real provider path end-to-end.
The turn loop and contract are already strong enough that the next milestone is
one working provider adapter, not more mock-only planning.

2. Keep the model grounded in Unicorn context.
Before expanding capabilities, make sure the system prompt, tool descriptions,
and rendered notes keep the agent scoped to:

- current datasets
- current filters
- current visible tree / current backend context
- explicit tool outputs

3. Add one or two high-value read-only tools.
Best candidates:

- `get_subtree_report`
- `expand_taxon`

These make the agent much more useful without giving it uncontrolled powers.

4. Connect agent actions back into the analysis UI more clearly.
For example:

- when the agent focuses a taxon, surface that in the transcript/evidence area
- when the agent uses table or subtree-report data, keep the corresponding view
  visible and labeled as the grounding source


Longer-term directions
----------------------

1. Backend-proxied provider mode.
Likely needed once we want:

- safer auth handling
- shared server-side sessions
- audit logging
- rate-limit control

2. Agent-facing backend analysis endpoints.
Once the current graph-native tools are stable, the backend can expose richer
analysis payloads specifically designed for agent consumption.

3. Multi-step guided workflows.
Examples:

- "inspect this subtree"
- "compare these two selected clades"
- "rank-collapse the current selection and summarize differences"

These should still remain human-first and inspectable.


Recommended next order
---------------------

1. Remove local-vs-remote semantic drift from the agent layer
2. Implement one real provider adapter
3. Stabilize provider error/auth behavior
4. Add `get_subtree_report`
5. Add `expand_taxon` and optional highlight tools
6. Improve transcript/evidence clarity
7. Decide when provider calls should move behind the backend
