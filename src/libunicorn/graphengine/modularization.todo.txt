Unicorn Graphengine Modularization Pass
=======================================

Goal
----

Split `graphengine.js` into smaller browser-side modules without changing the
product model:

- backend-required runtime remains the only supported semantic mode
- backend remains the source of truth for datasets, taxonomy, visible tree,
  reports, and provider transport
- browser remains responsible for rendering, transient UI state, and local
  interaction

This is not a rewrite. It is a controlled extraction pass.


Why This Pass Is Needed
-----------------------

`graphengine.js` is currently about 4200 lines and still mixes:

- DOM wiring
- runtime state
- backend fetches
- tree transformation
- SVG rendering
- selection semantics
- report rendering
- agent context/tool loop
- resizing and panel behavior
- logging and status updates

That makes regressions hard to localize. The goal is to separate concerns
without introducing a build system, framework migration, or semantic changes.


Non-Negotiable Constraints
--------------------------

1. No bundler in this pass.
Keep the current lightweight workflow:

- `python3 -m http.server 8081`
- `python server_app.py`
- plain browser scripts loaded from `index.html`

2. No parallel local-mode architecture.
Do not modularize old local-vs-remote branching. Remove drift, do not package
it more neatly.

3. No behavioral rewrite during extraction.
Each pass should move or rename ownership, not redesign features at the same
time.

4. Preserve current served-page behavior.
The E2E suite is now part of the contract and must stay green after each pass.

5. Keep the provider adapter separate.
`graphengine_provider_adapter.js` already defines one useful seam and should
remain independent.


Recommended Module Format
-------------------------

Use browser scripts with one shared namespace on `window`.

Recommended namespace:

- `window.UnicornGraphEngine`

Recommended pattern per file:

- each file is an IIFE
- each file reads `window.UnicornGraphEngine`
- each file adds one small group of functions/state
- only the boot file performs final event binding and startup

Why this format:

- no bundler required
- keeps script loading explicit in `index.html`
- compatible with the current development workflow
- consistent with the existing provider adapter module style

Do not switch to an ES-module-only architecture in the first pass. That would
add a second migration at the same time as the modularization itself.


Target Directory / File Layout
------------------------------

Recommended browser-side split:

- `graphengine_core.js`
- `graphengine_state.js`
- `graphengine_dom.js`
- `graphengine_backend.js`
- `graphengine_tree_model.js`
- `graphengine_tree_render.js`
- `graphengine_selection.js`
- `graphengine_reports.js`
- `graphengine_agent.js`
- `graphengine_ui.js`
- `graphengine_boot.js`

Keep:

- `graphengine_provider_adapter.js`

Transitional rule:

- during the pass, `graphengine.js` may remain as a shrinking compatibility
  shell until the last step
- final target is for `graphengine.js` to disappear or become a tiny legacy
  loader that delegates to `graphengine_boot.js`

Dependency Rules
----------------

Allowed dependency direction:

- core -> nobody
- state/dom -> core
- backend -> core/state/dom
- tree_model -> core/state
- tree_render -> core/state/dom/tree_model
- selection -> core/state/tree_model/backend/tree_render
- reports -> core/state/dom/backend/selection
- agent -> core/state/dom/backend/selection/reports
- ui -> core/state/dom/backend/reports/tree_render
- boot -> everyone

Do not allow:

- backend importing agent logic
- tree render owning backend fetch policies
- reports re-implementing selection traversal
- UI resize code mutating backend semantics


Explicit State Ownership Rules
------------------------------

Backend-owned semantic state:

- dataset names and selected datasets after backend normalization
- taxonomy file identity
- visible tree payload
- effective expanded taxids when returned by backend context
- node counts and subtree totals
- report payload data

Browser-owned transient UI state:

- panel open/closed state
- drag-to-pan offsets
- hover state
- tooltip timing
- selected rows and selected nodes
- pending click timers
- transcript scroll position

Transitional but should trend backend-owned:

- `minReadsActual`
- `state.remote.requestContext`
- current report refresh scope


Proposed Extraction Order
-------------------------

Pass 0. Freeze contracts before moving code

Tasks:

- add this document
- add one short note in code comments near the top of `graphengine.js`
  declaring that it is in modularization transition
- keep E2E tests green before starting extraction

Exit criteria:

- no behavior change


Pass 1. Introduce namespace and boot shell

Tasks:

- create `window.UnicornGraphEngine`
- move `state` creation into `graphengine_state.js`
- move `els` lookup into `graphengine_dom.js`
- create `graphengine_boot.js`
- keep most functions still in `graphengine.js`, but route startup through boot

Why first:

- this creates a stable landing zone for future extractions

Regression gate:

- `test_connectbackend.py`
- `test_render.py`


Pass 2. Extract core helpers and UI shell logic

Tasks:

- move constants and pure helpers into `graphengine_core.js`
- move sidebar, section toggles, slider controls, and resizing into
  `graphengine_ui.js`
- keep render/backend semantics untouched

Regression gate:

- `test_connectbackend.py`
- `test_render.py`
- manual check: panel toggles, count view, min-reads UI still react correctly


Pass 3. Extract backend runtime layer

Tasks:

- move connection, dataset refresh, upload, backend fetch helpers, and request
  context helpers into `graphengine_backend.js`
- stop allowing backend fetch helpers to live in render/report code

Most important outcome:

- one file becomes the authority for backend IO and normalized backend context

Regression gate:

- `test_connectbackend.py`
- `test_render.py`
- manual check: dataset selection changes still refresh the visible tree


Pass 4. Extract tree model and rendering separately

Tasks:

- move tree transformation and traversal helpers into
  `graphengine_tree_model.js`
- move SVG drawing, pan/center, and tooltip display into
  `graphengine_tree_render.js`

Important caution:

- do not mix `buildRemoteTree()` with `renderSvg()` in the same extraction
  unless the interface between them is explicit

Regression gate:

- `test_render.py`
- manual check: tooltip, center-root, expand/collapse still behave


Pass 5. Extract selection semantics

Tasks:

- move selection/focus/uncollapse/select-to-rank logic into
  `graphengine_selection.js`
- make `reports` and `agent` consume selected nodes through exported helpers

This is a high-risk pass.

Why:

- recent regressions touched exactly this area

Recommended approach:

- do this in subpasses, not in one large move
- extract selection semantics first
- rewire reports and agent second
- avoid mixing report rendering edits into the same patch that moves selection
  mutation logic

Pass 5A. Freeze the selection contract

Goal:

- define one explicit browser-side API for selection semantics before moving
  code

Tasks:

- create `graphengine_selection.js`
- add a short module header comment that states the public ownership:
  selected nodes, focus node, uncollapse flows, descendant selection,
  select-to-rank flows
- define the exported interface shape first, even if implementation still
  forwards into existing functions temporarily

Required public helpers for V1 extraction:

- `getSelectedNodes()`
- `getSingleSelectedNode()`
- `hasSelection()`
- `getFocusedNode()`
- `toggleSelection(node)`
- `clearSelection()`
- `toggleFocus(node)`
- `selectDescendants()`
- `uncollapseSelected()`
- `uncollapseSelectedToTips()`
- `selectToRank()`
- `updateSelectToRankOptions()`

Important caution:

- the contract should expose semantic helpers, not raw internal Sets unless
  there is no alternative
- `state.selected` may continue to exist internally, but new consumers should
  stop treating it as the public API

Exit criteria:

- `graphengine_selection.js` exists
- no intended behavior change
- no consumer rewiring yet beyond safe namespace plumbing

Pass 5B. Move core selection semantics

Goal:

- make one file the authority for selection state mutation and selection-side
  redraw/status consequences

Tasks:

- move these functions into `graphengine_selection.js`:
  `getSelectedNodes()`
  `getSingleSelectedNode()`
  `toggleSelection()`
  `clearSelection()`
  `toggleFocus()`
  `selectDescendants()`
  `uncollapseSelected()`
  `uncollapseSelectedToTips()`
  `selectToRank()`
  `updateSelectToRankOptions()`
- move any helper logic that computes valid selection targets, descendant
  walks, rank options, or focus transitions with them
- keep redraw, status updates, and table clearing inside the selection module
  when they are a direct consequence of selection semantics

Important caution:

- do not move report generation in this subpass
- do not change how multi-selection is represented
- do not change modifier-click or double-click semantics

Allowed temporary pattern:

- `graphengine.js` may still own the button event wiring while calling into
  `selection.*`

Exit criteria:

- selection mutations live in `graphengine_selection.js`
- `graphengine.js` no longer owns the semantic body of selection operations
- ctrl/cmd-click selection, double-click focus, and uncollapse still behave

Regression gate after 5B:

- `test_rank_dropdown.py`
- manual check: count matrix path still starts from a multi-selection produced
  by `Select To Rank`

Pass 5C. Rewire reports and agent to consume exported selection helpers

Goal:

- remove direct consumer reasoning over raw selection state where practical

Tasks:

- make report entrypoints use:
  `getSelectedNodes()`
  `getSingleSelectedNode()`
  `hasSelection()`
- make agent tool handlers use exported selection helpers instead of reading
  `state.selected` directly when a semantic helper already exists
- keep UI-only enable/disable checks allowed to read simple booleans if that is
  the least risky path, but prefer helper-based checks when already available

Important caution:

- do not move popup rendering or count-matrix rendering into this pass; that
  belongs to Pass 6
- do not redesign agent tools during this pass

Exit criteria:

- report and agent callers depend on selection exports rather than ad hoc tree
  traversal in their own files
- selection ownership is clearer even if some small UI-only state reads remain

Regression gate after 5C:

- `test_rank_dropdown.py`
- `test_selection_reports.py`
- manual check: count matrix still accepts multi-selection and barplot/PCoA
  still open

Pass 5D. Trim leftover direct selection access

Goal:

- make remaining direct `state.selected` access obviously UI-only or internal
  to the selection module

Tasks:

- review `graphengine.js`, `graphengine_reports.js` future extraction points,
  and agent callers for leftover direct selection access
- leave alone any harmless UI-only checks if replacing them would add risk
- remove duplicate helper logic that selection module now owns

Definition of success for Pass 5:

- one module owns selection semantics
- reports and agent consume selection through exported helpers
- multi-selection behavior remains unchanged
- select-to-rank remains stable under E2E coverage
- this pass does not also become a reports refactor

Implementation notes:

- safest ordering inside the code move:
  export shell first
  move pure helpers next
  move state mutation functions next
  rewire button handlers last
- when in doubt, keep semantic side effects together:
  selection mutation
  redraw
  status text
  rank-option refresh
  report invalidation
- do not split those apart yet unless the interface is extremely obvious

Regression gate:

- `test_rank_dropdown.py`
- `test_selection_reports.py`
- manual check: count matrix still accepts multi-selection


Pass 6. Extract reports

Tasks:

- move subtree/rank report logic, matrix rendering, popup generation, and
  export flows into `graphengine_reports.js`
- keep count-mode interpretation centralized here

Regression gate:

- `test_selection_reports.py`
- manual check: count matrix, barplot, and PCoA still open correctly


Pass 7. Extract agent runtime

Tasks:

- move agent UI state, transcript rendering, context building, tool registry,
  and turn-loop logic into `graphengine_agent.js`
- keep provider transport in `graphengine_provider_adapter.js`

Important caution:

- do not expand agent capability in the same pass
- first extract, then improve

Recommended approach:

- split this into three extraction subpasses plus one cleanup pass
- move transcript/UI behavior first
- move context builder and tool registry second
- move provider turn-loop orchestration third
- trim leftover direct agent access last

Why this ordering:

- transcript rendering is the safest visible slice
- context/tool registry has the highest contract value for later work
- the turn loop is the riskiest part and should move only after the first two
  boundaries are stable

Pass 8. Delete the monolith shell

- move boot/wiring first
- trim compatibility globals second
- remove the monolith shell last

Why this ordering:

- boot extraction is the safest remaining slice
- compatibility removal is easier once startup ownership is explicit
- deleting `graphengine.js` should be the final confirmation, not the first move

Pass 8A. Move remaining startup and wiring into `graphengine_boot.js`

Goal:

- make one file the authority for browser startup order and event binding

Tasks:

- move the remaining initialization shell out of `graphengine.js` into
  `graphengine_boot.js`
- move top-level boot concerns such as:
  provider adapter creation
  registry exposure
  startup event binding
  initial render/log/status sync calls
- keep module ownership unchanged:
  boot should wire modules together, not absorb their logic
- keep compatibility globals that tests or DevTools still use:
  `window.unicornAgentRegistry`
  `window.unicornAgentProviderAdapter`
  `window.handleAgentSend`

Important caution:

- do not remove compatibility globals in this subpass
- do not mix startup rewiring with feature work
- if a helper still contains semantics, move that semantic body into the proper
  module first rather than hiding it in boot

Exit criteria:

- `graphengine_boot.js` owns startup order and event binding
- `graphengine.js` no longer owns meaningful initialization logic
- existing page load behavior is unchanged
