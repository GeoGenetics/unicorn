Unicorn Graphengine TODO

Current State

- Graphengine is now backend-authoritative and backend-required.
- The browser UI is modularized and `graphengine.js` has been removed.
- `graphengine_boot.js` owns startup and browser-side integration.
- The backend is the source of truth for:
  - uploaded datasets
  - taxonomy files
  - tree construction
  - visible tree slicing
  - tooltip and table payloads
  - count matrix and rank report payloads
  - compute-backed barplot and PCoA payloads
- The browser is responsible for:
  - interaction
  - view state
  - popup rendering
  - agent transcript display
  - provider configuration UI
- The current UI already supports:
  - backend connection and upload flow
  - tree rendering and navigation
  - selection workflows including `select to rank`
  - count-view toggle for direct vs cumulative counts
  - count matrix and rank report
  - barplot and PCoA popups
  - agent panel with provider-backed execution path
- The current compute layer already exists under `unicorn_compute` and is the intended home for future analysis routines.

Guiding Priorities

- Prefer features that improve the value of the whole app, not one narrow path.
- Keep backend-as-truth intact.
- Keep provider integrations thin and provider-neutral where possible.
- Prefer additions that strengthen both manual analysis and future agent workflows.
- Avoid large infrastructure detours until they unlock visible user value.

Active Product Direction

0. Robust backend-native expansion actions
1. Metadata-aware analysis
2. Agentic graphengine
3. Better selection-driven exploration
4. More analysis features through `unicorn_compute`
5. Only then deeper infrastructure or optimization work

Concrete Roadmap

DONE 0. Backend-Native Large Expansion Actions

Why first:
- current `Uncollapse Tips` can fail on real datasets because the browser sends very large expansion state through `GET` query parameters
- large clades such as `2759` can overflow request-size limits before the backend even parses the request
- this is a reliability issue in existing core functionality, not just a future optimization

Short plan:
- move large expansion actions off long `GET` URLs
- make `Uncollapse Tips` a backend-native action with request-body transport
- keep the backend responsible for computing large descendant expansion state
- preserve current visible-tree behavior while making the transport scalable

Definition of done for this phase:
- `Uncollapse Tips` works for large clades on a real backend session
- the browser no longer serializes giant `expanded=` query strings for this action
- client and server logs stay understandable when large expansion actions run

DONE 1. Metadata Integration

Why first:
- highest immediate value
- improves tree interpretation, reports, plots, and future agent answers
- unlocks real biological/sample grouping workflows

First implementation slice:
- add one metadata table input format for per-sample annotations
- load metadata into backend session state
- expose metadata summary in the UI
- attach metadata to selected datasets by stable dataset name
- show metadata in dataset list and key report views

Second slice:
- color/group datasets by metadata field
- show metadata-aware legends in count matrix, barplot, and PCoA
- allow one metadata field to drive plot grouping

Definition of done for this phase:
- graphengine can load metadata for selected datasets
- users can see metadata in the interface
- tree, barplot, and PCoA reuse one shared metadata resolver contract
- value-level metadata colors, including the missing bucket, are reusable across visualizations

Current closure note:
- metadata is now backend-owned and additive
- metadata attaches to datasets by filename
- selected datasets show metadata in the controls UI
- the tree exposes a metadata-aware legend in the main UI
- barplot and PCoA consume the same resolver-driven label/color payload as the tree
- further metadata-aware agent summaries should now be treated as agent work, not unfinished metadata integration

2. Agentic Graphengine

Why second:
- fast payoff
- lowers provider cost and latency
- improves reliability before adding more agent behaviors
- builds directly on the provider-neutral strict-JSON contract and the now-stable metadata-aware graph context

First implementation slice:
- shrink graph context to selected, focused, visible, and summary-only data
- stop resending redundant payloads
- cap transcript history aggressively
- summarize tool results before reinjection into the next turn
- keep the provider request/response loop auditable while reducing payload size

Second slice:
- add compact provider context mode as the default
- instrument approximate request size and tool-result size in logs
- keep one debug mode for full payload inspection
- prepare the compact context so future agent actions can consume the same graph state without re-expanding payload size

Third slice:
- enrich agent context with compact metadata-aware summaries
- keep using backend-authoritative graph state and resolver-derived metadata summaries
- do not dump raw metadata tables into provider turns
- stage the system for later safe agent actions once compact execution is reliable

Definition of done for this phase:
- agent turns are visibly smaller
- repeated prompts do not resend the whole graph state
- logs still support debugging without flooding the normal UI
- the compact context remains rich enough for useful graph-aware answers
- the agent stack is ready for the next phase of safe graph actions

3. Safe Agent Actions

Why third:
- biggest perceived leap in usefulness after token compaction
- builds directly on the existing read-only tool contract and provider wiring

First implementation slice:
- add explicit action tools for:
  - `select_node`
  - `clear_selection`
  - `select_descendants`
  - `select_to_rank`
  - `open_count_matrix`
- keep actions narrow, deterministic, and UI-visible

Second slice:
- add action confirmation/result reporting back into transcript
- make failures explicit when the requested graph action cannot be performed
- keep unsupported mutations clearly rejected

Definition of done for this phase:
- the agent can carry out a small safe set of visible graph actions
- transcript and client log make those actions auditable

4. Selection UX Upgrade

Why fourth:
- strong manual-usage payoff
- complements metadata and report workflows
- relatively low technical risk

First implementation slice:
- add clearer selection summary in the top or side UI
- show what selection scope current reports will use
- improve feedback after selection operations

Second slice:
- add more selection operators such as:
  - `select visible`
  - `invert selection`
  - `select siblings`
  - `select path to root`

Definition of done for this phase:
- users can understand and refine selections without guesswork
- selection-driven reporting feels deliberate rather than implicit

5. Metadata-Aware Reporting and Plotting

Why here:
- once metadata exists, it should shape downstream analysis views
- this creates visible scientific value quickly

First implementation slice:
- metadata-driven grouping in barplot
- metadata labels in count matrix exports
- metadata labels and symbols in PCoA

Second slice:
- per-group summaries
- quick compare views between metadata-defined cohorts

Definition of done for this phase:
- reports and plots can be interpreted by sample identity, not just filename

6. Local LLM Provider Path

Why later:
- valuable, but easier once compact context and action semantics are stable
- should reuse the provider-neutral strict-JSON adapter design

First implementation slice:
- support one local provider target through backend transport
- keep the same Unicorn internal provider interface
- expose local provider config in the existing provider UI

Definition of done for this phase:
- graphengine can talk to at least one local LLM without changing agent semantics

7. Expand `unicorn_compute`

Why ongoing:
- this is the right long-term home for analysis features
- it keeps the frontend lighter and the backend more reusable

Near-term targets after current barplot and PCoA:
- richer PCoA controls and diagnostics
- additional ordination/summary plots
- backend-served compute specs for future visualizations

Potential next analyses:
- scree plot
- loadings or taxon contribution summaries where appropriate
- sample distance heatmap
- cohort comparison summaries

8. Performance and Scale

Do this after the above features unless a real bottleneck appears.

Current note:
- real backend sessions with many datasets and large visible clades can already feel slow
- tree dragging, large selection workflows, and downstream analysis popups work correctly but are not yet snappy at scale
- this is now a real product concern, but should be handled with measurement rather than panic refactoring

Performance investigation track:
- keep the main roadmap moving, especially metadata
- allow targeted performance work whenever ordinary interaction becomes clunky on real sessions
- prefer measurement-backed fixes over speculative optimization

First investigation pass:
- measure tree redraw time after large expansion workflows
- measure visible node count in realistic sessions such as:
  - many datasets selected
  - `Eukaryota` expanded to tips
  - genus-level selection
- measure time spent in:
  - visible-node collection
  - tree layout
  - SVG/DOM update cost
  - report refresh coupling
  - barplot/PCoA popup request and render time
- identify whether the dominant slowdown is:
  - frontend DOM/SVG size
  - full redraw frequency
  - repeated tree/layout recomputation
  - selection traversal cost
  - report synchronization cost

Likely first optimization target:
- frontend tree rendering and redraw behavior
- especially large SVG node/label counts and full redraw cost during pan/navigation

Measure first:
- render latency
- expand latency
- count matrix latency
- PCoA latency
- payload sizes for tree, tooltip, reports, and agent turns

Only then consider:
- cached visible tree slices
- cached compute outputs
- tooltip/report prefetch
- larger-session lifecycle policies

Current Non-Goals

- bringing back a local-only graphengine runtime
- adding broad state-mutating agent behaviors before safe action tooling is solid
- premature caching without measured hot paths
- deep provider-specific logic leaking into the main graph runtime

Recommended Implementation Order

DONE 0. Backend-native large expansion actions
1. Metadata integration
2. Agent token compaction
3. Safe agent actions
4. Selection UX upgrade
5. Metadata-aware reporting and plotting
6. Local LLM provider path
7. Continued `unicorn_compute` expansion

What “Good” Looks Like Next

- graphengine remains fast and understandable
- metadata makes the interface scientifically richer
- agent mode becomes cheaper, safer, and more useful
- new analyses land through `unicorn_compute`
- the codebase stays modular while visible user value keeps increasing
- performance work happens when real-session interaction quality demands it, guided by measurement
