Unicorn Graph Engine Agentic V1 Plan
====================================

Goal
----

Add an Agent panel to the graph engine UI so a human user can ask natural-
language questions about the current graph state, while a constrained agent
uses Unicorn-native data and UI actions to answer those questions.

V1 is intentionally limited to what Unicorn already knows how to do today.
This version is not a general scientific agent, not a causality engine, and
not a replacement for the UI. It is a guided analyst that can read current
graph context, call existing Unicorn capabilities, and reflect its findings
back into the visualization.


V1 Product Definition
---------------------

The V1 agent should be able to:

- read the current graph context
- answer questions about the current dataset selection and visible tree
- inspect nodes, tables, and subtree reports through Unicorn-native tools
- summarize findings in plain language
- highlight or focus relevant taxa back in the graph UI
- show its evidence trail so users can verify what it did

The V1 agent should not yet:

- invent new analysis methods
- access arbitrary local files
- make unsupported ecological or causal claims
- operate outside the current graph engine context
- modify datasets or backend files


Human-First Design Principles
-----------------------------

1. The graph engine remains a human tool first.
2. The agent must feel like a guided assistant inside the UI, not a hidden
   automation layer.
3. Every answer must be grounded in visible Unicorn state and backend data.
4. Every important agent action must be inspectable by the user.
5. The agent should drive existing UI views when possible instead of creating
   parallel hidden analysis state.


V1 User Experience
------------------

Primary interaction:

1. User loads data and renders a tree as usual.
2. User opens a new Agent panel in the graph engine.
3. User configures a model provider and model.
4. User asks a question such as:
   - "What taxa show the most damage?"
   - "Which visible subtree has the most reads?"
   - "Show me the strongest taxa in this clade."
5. The agent reads the current Unicorn context.
6. The agent uses a constrained set of Unicorn tools.
7. The UI shows:
   - the natural-language answer
   - the backend/tool calls made
   - the evidence used
   - relevant nodes highlighted or focused in the graph


V1 Scope Boundaries
-------------------

The agent will only use capabilities that already exist in the graph engine
and backend, or thin wrappers around them.

In-scope backend/context sources:

- current dataset selection
- current taxonomy files
- current min_reads filter
- current visible tree state
- current expanded nodes
- node tooltip data
- table view data
- subtree report data
- current backend dataset summaries
- current render-data payloads when needed

In-scope UI reflections:

- highlight taxa returned by the agent
- focus the graph on a chosen node
- expand a returned node in remote mode
- open or refresh the current count table
- open or refresh the subtree report panel
- show an evidence log in the Agent panel

Out of scope for V1:

- ecological niche shift inference
- environmental driver analysis
- geography-aware modeling
- freeform code execution
- autonomous multi-turn background jobs


Architecture Overview
---------------------

V1 should be split into five parts:

1. Agent panel UI
   A new frontend area for provider configuration, prompts, chat history, tool
   activity, and evidence.

2. Graph context snapshot
   A frontend-generated machine-readable summary of the current Unicorn state
   that the agent can consume.

3. Constrained Unicorn tool layer
   A small set of callable actions that map directly to existing backend
   endpoints and frontend graph actions.

4. Provider adapter
   A frontend abstraction for calling the chosen model provider with the same
   Unicorn tool contract.

5. Agent response renderer
   A frontend layer that renders answers, tool traces, evidence, and UI
   highlights/focus changes.


Concrete Work Plan
------------------

Phase 1. Define the agent contract

- Write down the exact responsibilities of the V1 agent.
- Define what "current graph context" means in machine-readable terms.
- Define the allowed tool list and forbid everything else.
- Decide what agent outputs are allowed:
  - prose answer
  - citations/evidence list
  - highlight taxids
  - focus taxid
  - request table view
  - request subtree report

Deliverable:
- a stable V1 JSON contract for context in, tool calls, and answer out


Phase 2. Add the Agent panel to the frontend

- Add a new Agent section to index.html.
- Add provider controls:
  - provider selector
  - API key or auth token field
  - model field
- Add a prompt textarea and submit button.
- Add a conversation/history area.
- Add a tool activity log area.
- Add an evidence/results area.
- Add status states:
  - idle
  - thinking
  - calling tools
  - error
  - complete

Deliverable:
- a visible Agent panel integrated into the current graph engine layout


Phase 3. Define and build the graph context snapshot

Create a single frontend function that gathers the current Unicorn state into
one compact object.

Minimum V1 context fields:

- rendering mode: local or remote
- selected dataset names
- loaded taxonomy file names
- min_reads
- current root or active subtree target if one exists
- currently selected nodes if any
- expanded taxids
- whether remote server tree mode is active
- tree summary:
  - total reads
  - direct taxa count
  - current visible root taxid and name
- backend availability flags

Optional V1 context fields:

- visible node list or a compact visible frontier summary
- last opened table scope
- last opened subtree report target

Deliverable:
- one canonical `buildAgentContext()` function in graphengine.js


Phase 4. Build the constrained Unicorn tool layer

Implement a small tool registry in the frontend. Each tool should be a thin,
predictable wrapper around existing graph engine behavior.

Recommended V1 tools:

- `get_graph_context`
  Returns the current frontend graph context snapshot.

- `list_selected_datasets`
  Returns selected datasets and current totals.

- `get_root_view`
  Returns the current visible root tree slice under active filters.

- `get_node_details`
  Returns tooltip payload for one node.
  Maps to `/node-tooltip` in remote mode and to equivalent local data in local
  mode if feasible.

- `get_table_view`
  Returns ranked rows for root or one node.
  Maps to `/table-view` in remote mode.

- `get_subtree_report`
  Returns the current subtree report payload for one node.
  Maps to `/subtree-report` in remote mode.

- `focus_taxon`
  Requests a graph focus/highlight action for one taxid.

- `highlight_taxa`
  Requests highlight state for a list of taxids.

- `expand_taxon`
  Expands one node when remote tree mode is active and the node is expandable.

- `clear_agent_highlights`
  Clears agent-generated highlight state.

Important V1 rule:

Do not let the model call arbitrary fetch URLs or arbitrary UI functions.
Everything must go through the small Unicorn tool registry.

Deliverable:
- one frontend tool registry with strict input/output shapes


Phase 5. Normalize local and remote behavior

The agent should feel consistent whether Unicorn is running in local parsing
mode or remote backend mode.

Work needed:

- decide which tools work in both modes
- decide which tools are remote-only in V1
- when a tool is unavailable in local mode, return a clean "not available in
  current mode" result instead of failing silently
- prefer reading from existing frontend state when it already contains the same
  information

Recommended V1 compromise:

- support basic graph context, dataset summaries, and focus/highlight actions in
  both modes
- support node details, table view, and subtree report best in remote mode
- clearly tell the user when a question requires remote backend context

Deliverable:
- a documented compatibility table for each tool in local vs remote mode


Phase 6. Add a provider adapter layer

Implement a provider abstraction so the Agent panel is not hardwired to one
vendor. This phase should be explicitly broken into a staged rollout.

Provider roadmap:

- V1: mock mode, then API-key-based provider adapter
- V2: Unicorn backend proxy for safer provider calls
- V3: real provider connection/auth flows if supported and worth the complexity

Phase 6A. Lock the provider abstraction before any real API integration

Define one provider interface in the frontend so the mock agent and any future
real provider share the same contract.

Minimum provider interface responsibilities:

- accept provider name, model name, and credentials or auth state
- accept the current system prompt, user prompt, graph context, and tool schema
- return:
  - assistant text
  - tool-call requests if any
  - provider or transport errors
- support a simple request loop shape that can later expand into true tool
  calling

Concrete tasks:

- define a `providerAdapter` interface in graphengine.js
- make the current mock mode implement that same interface
- keep the Agent transcript renderer unchanged regardless of provider

Deliverable:
- one stable provider adapter interface with `mock` as the first implementation


Phase 6B. V1 provider integration: API-key-based adapter

This is the first real model-provider milestone.

Scope:

- still compatible with the current client-side prototype architecture
- user manually provides provider credentials
- no provider-specific login flow yet
- OpenAI should be the first reference implementation

Concrete V1 tasks:

1. Add provider controls to the Agent panel:
   - provider selector
   - model field
   - API key field
   - provider mode indicator showing `mock` vs `live`

2. Keep `mock` as the default provider so Unicorn still works without any key.

3. Add a first real provider adapter implementation for OpenAI:
   - user enters an OpenAI API key
   - adapter sends prompt + context + tool schema
   - adapter returns assistant output in the same shape as mock mode

4. Keep tool execution under Unicorn control:
   - the provider may request Unicorn-native tool calls
   - Unicorn executes those calls locally through the registry
   - Unicorn sends tool results back through the adapter loop

5. Make the credential UX explicit:
   - label this as prototype mode
   - explain that the key is being used from the client side
   - do not silently persist the key

6. Add clear local-only failure states:
   - missing key
   - invalid key
   - network error
   - unsupported model/provider selection

Recommended V1 constraint:

- begin with one real provider implementation only
- OpenAI first
- keep other providers represented in the UI only after the abstraction is
  stable enough to support them honestly

Deliverable:
- a working `mock + OpenAI API key` provider layer in the Agent panel


Phase 6C. V2 provider integration: Unicorn backend proxy

This phase moves provider calls off the browser and into Unicorn-controlled
server infrastructure.

Why:

- better credential safety
- better request auditing
- cleaner rate-limit handling
- easier multi-user support
- easier future account/session management

Concrete V2 tasks:

- define one backend endpoint for agent-provider traffic
- move provider credentials to the backend or backend-managed secret storage
- let the frontend send only:
  - prompt
  - graph context
  - requested provider/model identity
- keep Unicorn-native tool execution explicit and inspectable
- preserve the same frontend transcript and tool-trace UX

Deliverable:
- provider traffic routed through Unicorn backend instead of direct client-side
  API calls


Phase 6D. V3 provider integration: real account/auth connection flows

This phase is only worth doing if the chosen providers actually support it and
if the product value justifies the complexity.

Goal:

- the user connects a provider account instead of manually pasting an API key

Possible V3 patterns:

- provider OAuth or equivalent delegated authorization
- Unicorn-managed saved provider connections
- user account settings page for connected providers

Important note:

Do not assume every provider supports a clean third-party "Sign in with X"
experience for API-backed use cases. This must be validated provider by
provider.

Deliverable:
- connected-provider UX where supported, without changing the Unicorn tool
  contract or transcript UX


Decision rules for the next implementation slice

- next coding step should be V1 only
- keep `mock` mode available at all times
- add the provider abstraction before adding any real networked provider
- treat OpenAI as the first concrete integration target
- defer backend proxy and login flows until the local provider loop is proven


Updated Step 5 in the Suggested Implementation Order

5. Add provider adapter in stages:
   - V1: mock mode, then API-key-based provider adapter
   - V2: Unicorn backend proxy for safer provider calls
   - V3: real provider connection/auth flows if supported and worth the complexity


Phase 7. Write the V1 system prompt and tool instructions

The model must be explicitly told:

- it is operating inside Unicorn Graph Engine
- it must only reason from current graph context and Unicorn tool outputs
- it must avoid claims not supported by returned evidence
- it should prefer tool use over guessing
- it must explain limitations when data is insufficient
- it may return UI action suggestions only from the allowed action schema

The system prompt should also explain the meaning of key Unicorn terms:

- direct reads
- subtree reads
- selected datasets
- min_reads filter
- visible tree
- current scope

Deliverable:
- one V1 system prompt string in the frontend codebase


Phase 8. Add answer rendering and evidence presentation

The Agent panel must render more than chat text.

Required answer sections:

- answer summary
- evidence used
- tool calls made
- current scope used
- limitations or caveats

Suggested evidence rendering:

- list of taxids and names referenced
- counts or damage metrics used
- links/buttons to focus those nodes
- buttons to open subtree report or count table for cited taxa

Deliverable:
- agent responses that are inspectable and navigable


Phase 9. Reflect agent results back into the graph

This is the heart of the human-first experience.

Implement agent-driven UI reflections:

- highlight a returned set of taxa in the tree
- scroll/focus to one returned focal node
- expand a node if the answer depends on revealing children
- populate the subtree report panel for a cited node
- populate the table panel for a cited scope

Important rule:

Agent-driven UI changes should be explicit and reversible. The user should be
able to clear agent highlights and continue manual exploration normally.

Deliverable:
- visible synchronization between the agent answer and the graph UI


Phase 10. Add safety, limits, and failure handling

V1 should fail clearly and safely.

Handle these cases:

- no datasets selected
- no taxonomy loaded
- question asks for unsupported analysis
- remote-only tool requested in local mode
- backend returns node_not_in_active_tree
- backend returns node_filtered_out
- provider authentication failure
- provider timeout
- malformed tool call from model

Design requirement:

Every failure shown to the user should say:

- what went wrong
- whether the issue is Unicorn state, provider state, or unsupported scope
- what the user can do next

Deliverable:
- agent UX that is legible under failure, not just under success


Phase 11. Test against real V1 question classes

Create a fixed set of supported V1 question patterns and test them end to end.

Recommended test prompts:

- "What taxa show the most damage?"
- "Which node in the current tree has the most subtree reads?"
- "Summarize this subtree."
- "Show the strongest taxa under this clade."
- "What does this node represent?"
- "Compare the top taxa in the current root table."

For each prompt, verify:

- the agent chooses valid tools
- the returned answer matches Unicorn data
- the answer cites the active scope and filters
- the graph highlights or focuses the relevant taxa
- the user can inspect the evidence path

Deliverable:
- a manual V1 acceptance checklist


Suggested Implementation Order
------------------------------

1. Add Agent panel UI shell.
2. Add graph context snapshot builder.
3. Add frontend Unicorn tool registry.
4. Add answer renderer with mock responses first.
5. Add provider adapter.
6. Add real tool-calling loop.
7. Add highlight/focus reflection into the graph.
8. Add failure handling and polish.
9. Run acceptance prompts and tighten the prompt/tool contract.


Recommended First Milestone
---------------------------

The first meaningful milestone should be:

"A user can ask a question about the current graph state, the model can call
one or more Unicorn-native tools, and the UI returns a grounded answer with
highlighted taxa and an inspectable evidence trail."

This is enough to prove the V1 concept without requiring broader scientific
reasoning infrastructure.


Open Design Questions
---------------------

These should be decided before full implementation:

1. Should provider credentials live only in memory, or may they be stored in
   browser localStorage?
2. Should V1 support local-mode tool parity, or should some agent features be
   explicitly remote-only?
3. Should the agent be allowed to trigger graph state changes automatically, or
   should some actions require a user confirmation click?
4. How should multi-node highlighting look visually so it does not conflict
   with current selection and hover states?
5. Should the Agent panel keep a per-session conversation history only, or a
   persistent history tied to the current dataset selection?


Definition of Done for V1
-------------------------

V1 is done when all of the following are true:

- the graph engine has a working Agent panel
- a user can configure a model provider and ask a question
- the agent can read current Unicorn context through a stable contract
- the agent can use only a constrained set of Unicorn-native tools
- answers are grounded in Unicorn data and current UI scope
- results can highlight or focus taxa in the graph
- the user can inspect tool calls, evidence, and limitations
- unsupported questions fail clearly rather than hallucinating
